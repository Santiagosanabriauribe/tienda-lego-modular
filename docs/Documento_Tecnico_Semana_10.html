Documento Técnico - Tienda en Línea Modular de LEGO

Introducción

El presente documento corresponde a la etapa de definición, planeación y diseño arquitectónico de una tienda en línea modular especializada en sets y coleccionables de LEGO. En esta fase se establecen el problema que se busca resolver, los objetivos del proyecto, su alcance, los requerimientos funcionales y no funcionales, el modelo conceptual de datos, la arquitectura general y la metodología de trabajo que orientará el desarrollo durante las semanas posteriores.

La propuesta parte de una arquitectura desacoplada en la cual el frontend y el backend serán desarrollados como aplicaciones independientes. Toda comunicación entre ambos componentes se realizará mediante una API REST, evitando que el backend genere o renderice directamente las vistas de la aplicación. Este enfoque responde a los lineamientos del proyecto académico, que exigen una separación real entre frontend y backend.

En cumplimiento de las condiciones de la Semana 10, este documento se limita a la planeación y definición del sistema. Por tanto, no se incluye implementación ni código fuente correspondiente a la aplicación final.

1. Planteamiento del problema

Los pequeños y medianos negocios dedicados a la comercialización de sets, figuras y artículos coleccionables de LEGO pueden comenzar sus actividades utilizando redes sociales, aplicaciones de mensajería instantánea o publicaciones independientes como principal mecanismo de venta. Aunque este modelo resulta suficiente para iniciar operaciones, presenta dificultades a medida que aumenta la cantidad de productos, categorías y clientes.

Uno de los principales problemas corresponde a la ausencia de un catálogo centralizado y organizado. Los productos LEGO pertenecen a distintas líneas y temáticas, como LEGO Star Wars, LEGO Technic, LEGO Marvel, LEGO City, LEGO Icons y LEGO Speed Champions. Cuando los productos son publicados únicamente mediante fotografías o publicaciones individuales en redes sociales, los clientes deben revisar gran cantidad de contenido para encontrar un producto específico y el negocio no dispone de una estructura adecuada para mantener la información organizada.

Esta problemática adquiere especial importancia en una tienda de LEGO porque determinados productos pueden tener existencias reducidas. Algunos sets descontinuados, minifiguras, ediciones especiales o coleccionables pueden disponer de pocas unidades, por lo que es necesario mantener actualizado el inventario para evitar ofrecer artículos agotados o generar pedidos por cantidades superiores a las disponibles.

Otro inconveniente se encuentra en el proceso manual de compra. Cuando las ventas se coordinan mediante mensajes privados, el cliente debe indicar individualmente cada artículo que desea comprar y el vendedor debe calcular manualmente cantidades, precios y valor total. Además de generar trabajo adicional, este mecanismo aumenta la posibilidad de errores y dificulta ofrecer una experiencia de compra consistente.

También existe una problemática administrativa. Las modificaciones de productos, precios, categorías y existencias deben realizarse manualmente en diferentes publicaciones o canales. La información puede quedar desactualizada o ser inconsistente entre distintos medios de comunicación.

Por esta razón se propone desarrollar una tienda en línea modular especializada en LEGO, que permita centralizar la administración del catálogo, organizar los productos mediante categorías o temáticas, gestionar sus existencias, permitir que los visitantes consulten y filtren los productos y proporcionar un carrito de compras que calcule automáticamente los valores asociados a una compra.

La aplicación será construida mediante una arquitectura cliente-servidor desacoplada, con un backend encargado de gestionar los datos y las reglas del negocio y un frontend independiente encargado de proporcionar la interfaz utilizada por los clientes y administradores.

2. Objetivos

2.1 Objetivo general

Diseñar, construir y desplegar una plataforma web de comercio electrónico especializada en sets y coleccionables de LEGO mediante una arquitectura desacoplada, conformada por un backend basado en una API REST y un frontend independiente que consuma sus servicios, permitiendo administrar productos y categorías, consultar un catálogo público, gestionar un carrito de compras y aplicar mecanismos adecuados de seguridad, documentación y despliegue.

2.2 Objetivos específicos

  1. Diseñar e implementar un backend basado en servicios REST que permita administrar la información relacionada con categorías, productos LEGO, existencias y operaciones del carrito, manteniendo una separación clara entre lógica de negocio, acceso a datos y exposición de servicios.
  2. Desarrollar un frontend independiente y dinámico que consuma la API REST del backend y permita a los visitantes navegar por el catálogo de LEGO, consultar productos por categoría y administrar los elementos agregados a su carrito sin depender de vistas generadas desde el servidor.
  3. Implementar un módulo administrativo que permita gestionar mediante una interfaz gráfica las categorías y productos disponibles, incluyendo operaciones de creación, consulta, actualización y eliminación.
  4. Aplicar mecanismos de seguridad web mediante el uso de HTTPS, prácticas de mitigación de ataques XSS y mecanismos de protección frente a solicitudes CSRF en aquellas operaciones que modifiquen información.
  5. Documentar la API mediante OpenAPI/Swagger, facilitando que desarrolladores o terceros puedan conocer, comprender y probar los servicios disponibles sin necesidad de consultar directamente el código fuente.
  6. Preparar y desplegar la aplicación en un entorno accesible, de forma que la solución completa pueda utilizarse desde equipos diferentes a los computadores de desarrollo de los integrantes del proyecto.

3. Alcance del proyecto

3.1 Funcionalidades incluidas

La primera versión de la Tienda en Línea Modular de LEGO comprenderá las funcionalidades necesarias para proporcionar una experiencia básica pero funcional de comercio electrónico.

El sistema incluirá un catálogo público de productos LEGO, donde cada producto estará asociado a una categoría o temática. Se contemplarán categorías como LEGO Star Wars, Technic, Marvel, City, Icons y Speed Champions, aunque el administrador podrá crear nuevas categorías según las necesidades de la tienda.

Cada producto podrá contener información básica como nombre, descripción, precio, cantidad disponible, número o referencia del set e imagen asociada.

  • Gestión de categorías LEGO mediante operaciones de creación, consulta, actualización y eliminación.
  • Gestión de productos o sets LEGO mediante operaciones CRUD.
  • Asociación de cada producto con una categoría determinada.
  • Catálogo público navegable y filtrado de productos según categoría.
  • Visualización de información detallada de cada producto.
  • Carrito de compras con adición, eliminación y modificación de cantidades.
  • Cálculo automático del subtotal y total del carrito.
  • Validación básica de disponibilidad de unidades.
  • Panel administrativo para productos y categorías.
  • Documentación de servicios mediante Swagger/OpenAPI.
  • Separación completa entre frontend y backend con intercambio de información en JSON.
  • Controles relacionados con HTTPS, XSS y CSRF.
  • Uso de CSS3 para los estilos del frontend, con migración a SCSS prevista para la Semana 14.
  • Despliegue final en un entorno accesible.

3.2 Funcionalidades fuera del alcance

Con el objetivo de mantener un alcance viable dentro del periodo académico, la primera versión no incluirá las siguientes capacidades:

  • Integración con una pasarela bancaria real o cobros reales mediante tarjetas débito o crédito.
  • Integración directa con PayPal, Stripe, Mercado Pago u otras plataformas financieras.
  • Procesamiento contable o generación de facturación electrónica ante entidades tributarias.
  • Integración automática con empresas transportadoras.
  • Rastreo GPS o satelital de pedidos.
  • Aplicación móvil nativa para Android o iOS.
  • Marketplace que permita registrar vendedores externos.
  • Sistema avanzado de recomendaciones mediante inteligencia artificial.
  • Integración automática con el catálogo oficial de LEGO.
  • Sincronización automática con tiendas físicas.
  • Programa avanzado de puntos o fidelización.
  • Procesamiento de devoluciones bancarias.
  • Sistema de subastas para coleccionables.

Estas características pueden considerarse como posibles extensiones futuras, pero no forman parte del alcance del proyecto académico actual.

4. Requerimientos del sistema

4.1 Requerimientos funcionales

RF-01. Gestión de categorías LEGO

El sistema deberá permitir al administrador crear, consultar, modificar y eliminar categorías utilizadas para organizar los productos de la tienda.

Cada categoría deberá disponer como mínimo de un identificador único, nombre y descripción. Entre los ejemplos de categorías se encuentran Star Wars, Technic, Marvel, City, Icons y Speed Champions.

RF-02. Gestión de productos o sets LEGO

El sistema deberá permitir al administrador registrar, consultar, actualizar y eliminar productos LEGO.

  • Identificador.
  • Nombre.
  • Número o referencia del set.
  • Descripción.
  • Precio.
  • Stock disponible.
  • Imagen.
  • Categoría.

Las operaciones realizadas deberán mantenerse sincronizadas entre la interfaz administrativa y la información almacenada en el sistema.

RF-03. Asociación entre productos y categorías

Cada producto deberá estar asociado a una categoría LEGO existente. Una categoría podrá contener múltiples productos, mientras que cada producto pertenecerá a una categoría principal.

RF-04. Visualización del catálogo público

El sistema deberá proporcionar una vista pública del catálogo sin exigir acceso al panel administrativo. El catálogo deberá mostrar información básica de los productos, como imagen, nombre, categoría, precio y disponibilidad.

RF-05. Filtrado de productos por categoría

El visitante deberá poder seleccionar una categoría y visualizar exclusivamente los productos pertenecientes a ella.

RF-06. Consulta del detalle de producto

El sistema deberá permitir consultar la información individual de un producto. La vista deberá presentar como mínimo el nombre, referencia del set, categoría, descripción, precio, imagen y unidades disponibles.

RF-07. Gestión del carrito de compras

El cliente deberá poder agregar productos disponibles al carrito. El carrito deberá permitir almacenar simultáneamente distintos productos.

  • Producto.
  • Cantidad.
  • Precio unitario.
  • Subtotal.

RF-08. Actualización del carrito

El usuario deberá poder modificar la cantidad de unidades de un producto previamente agregado y eliminar productos que ya no desee comprar. El sistema deberá actualizar automáticamente el valor total después de cualquiera de estas operaciones.

RF-09. Validación de disponibilidad

Antes de aceptar una cantidad determinada dentro del carrito, el sistema deberá comprobar que la cantidad solicitada no exceda las unidades disponibles del producto. Cuando un producto no tenga unidades disponibles deberá identificarse como agotado y no deberá permitir aumentar su cantidad dentro del carrito.

RF-10. Panel administrativo

El sistema deberá disponer de un panel de administración desde el cual una persona autorizada pueda gestionar categorías y productos mediante interfaces gráficas. Las operaciones deberán realizarse sin necesidad de utilizar herramientas técnicas externas como Postman o modificar directamente el código.

RF-11. Exposición de servicios REST

El backend deberá proporcionar los recursos necesarios mediante endpoints REST para permitir que el frontend consulte y modifique los datos correspondientes. El backend no deberá generar las vistas del frontend.

RF-12. Documentación de la API

Los endpoints disponibles deberán documentarse mediante OpenAPI/Swagger. La documentación deberá permitir identificar recursos, métodos HTTP, parámetros, cuerpos de las solicitudes y posibles respuestas. Un tercero deberá poder comprender y probar los servicios sin inspeccionar el código fuente.

4.2 Requerimientos no funcionales

RNF-01. Arquitectura desacoplada

El sistema deberá estar compuesto por dos aplicaciones independientes: un frontend responsable de la interfaz de usuario y experiencia de navegación, y un backend responsable de la lógica del negocio, persistencia de datos y exposición de servicios REST. Toda comunicación entre ambos deberá realizarse mediante peticiones HTTP a la API.

RNF-02. Formato de intercambio de datos

La información intercambiada entre frontend y backend deberá utilizar principalmente el formato JSON, facilitando la interoperabilidad entre ambas aplicaciones.

RNF-03. Seguridad

La solución deberá incorporar mecanismos para disminuir riesgos asociados con vulnerabilidades comunes de aplicaciones web.

  • HTTPS para proteger la información durante su transmisión.
  • Mitigación de ataques Cross-Site Scripting (XSS).
  • Protección frente a Cross-Site Request Forgery (CSRF) en operaciones que modifiquen información.

RNF-04. Documentación

La API REST deberá contar con documentación OpenAPI/Swagger actualizada de acuerdo con los servicios implementados, indicando métodos HTTP, parámetros, recursos, respuestas y estructuras principales utilizadas.

RNF-05. Usabilidad

La interfaz deberá diseñarse de manera que las funciones principales puedan ser utilizadas por personas que no posean conocimientos técnicos. La navegación entre catálogo, categorías, carrito y panel administrativo deberá ser clara y consistente.

RNF-06. Rendimiento

En condiciones normales de uso académico, las operaciones habituales de consulta del catálogo y actualización del carrito deberán responder de manera suficientemente rápida para no afectar la experiencia del usuario. La aplicación deberá evitar solicitudes innecesarias y transferencias excesivas de información.

RNF-07. Estilos mediante SCSS

La capa visual del frontend utilizará inicialmente CSS3 plano. Se prevé la migración a SCSS como preprocesador CSS en la Semana 14, conforme al cronograma del proyecto.

RNF-08. Mantenibilidad

La solución deberá organizarse mediante componentes y responsabilidades claramente separadas, de modo que futuras funcionalidades puedan incorporarse sin modificar innecesariamente módulos no relacionados.

RNF-09. Compatibilidad

El frontend deberá poder utilizarse desde navegadores web modernos y adaptarse correctamente a diferentes dimensiones de pantalla.

RNF-10. Disponibilidad para sustentación

La aplicación final deberá encontrarse desplegada o ejecutándose desde un entorno accesible externamente, de manera que los usuarios no dependan del computador particular de uno de los integrantes del equipo.

5. Modelo de datos

Para la primera versión del proyecto se proponen cuatro entidades conceptuales principales: Categoria, encargada de clasificar los productos; Producto, que representa un set o coleccionable LEGO disponible en el catálogo; Carrito, encargado de agrupar temporalmente los productos seleccionados; e ItemCarrito, entidad embebida que representa un producto específico y su cantidad dentro de un carrito.

Nota sobre la tecnología de persistencia: El proyecto utiliza MongoDB (base de datos documental NoSQL) en lugar de una base de datos relacional. Los identificadores son cadenas de texto generadas automáticamente por MongoDB (ObjectId), no números secuenciales. ItemCarrito se almacena como un subdocumento embebido dentro de cada documento Carrito, no como una colección independiente.

5.1 Entidad Categoria

AtributoTipoDescripción
idStringIdentificador único (ObjectId de MongoDB)
nombreStringNombre de la categoría (obligatorio)
descripcionStringDescripción de la categoría
activaBooleanEstado de disponibilidad (por defecto: true)

Una categoría puede contener múltiples productos. Relación: Categoria 1:N Producto.

5.2 Entidad Producto

AtributoTipoValidaciónDescripción
idString—Identificador único (ObjectId de MongoDB)
nombreStringObligatorioNombre comercial
numeroSetString—Número oficial o referencia del set
descripcionString—Descripción del producto
precioBigDecimalObligatorio, positivoPrecio unitario
stockIntegerObligatorio, ≥ 0Cantidad disponible
imagenUrlString—Ruta o URL de la imagen
activoBoolean—Disponibilidad en catálogo (por defecto: true)
categoriaIdStringObligatorioReferencia al identificador de la categoría asociada

Cada producto pertenece a una categoría principal. La relación se establece almacenando el identificador de la categoría (categoriaId) como referencia dentro del documento del producto.

5.3 Entidad Carrito

AtributoTipoDescripción
idStringIdentificador único (ObjectId de MongoDB)
fechaCreacionLocalDateTimeFecha y hora de creación (automática)
estadoStringEstado actual (por defecto: "ACTIVO")
totalBigDecimalValor total calculado del carrito
itemsList<ItemCarrito>Lista de ítems embebidos en el carrito

Un carrito contiene múltiples ítems como subdocumentos embebidos. El total se recalcula automáticamente al agregar, modificar o eliminar ítems.

5.4 Entidad ItemCarrito (embebida)

AtributoTipoDescripción
productoIdStringReferencia al identificador del producto
productoNombreStringNombre del producto (desnormalizado para visualización)
cantidadintUnidades seleccionadas
precioUnitarioBigDecimalPrecio del producto al momento de agregar
subtotalBigDecimalPrecio unitario multiplicado por cantidad

ItemCarrito no es una colección independiente en la base de datos. Se almacena como un arreglo de subdocumentos dentro de cada documento Carrito. Esto sigue el patrón de diseño de documentos embebidos propio de MongoDB, donde los datos que se acceden juntos se almacenan juntos.

5.5 Relaciones entre entidades

  • Categoria → Producto (1 a muchos): Una categoría puede tener muchos productos. Cada producto almacena el categoriaId de su categoría.
  • Carrito → ItemCarrito (1 a muchos, embebido): Un carrito contiene una lista de ítems dentro del mismo documento. Los ítems no existen de forma independiente fuera del carrito.
  • Producto → ItemCarrito (referencia): Cada ítem del carrito referencia a un producto mediante su productoId.

6. Arquitectura general del sistema

6.1 Arquitectura cliente-servidor desacoplada

La aplicación utilizará una arquitectura cliente-servidor desacoplada. Esto significa que el frontend y el backend funcionarán como proyectos diferentes y podrán evolucionar de forma relativamente independiente.

El flujo general de información será: Usuario → Frontend → API REST → Backend → Base de datos. La respuesta seguirá el recorrido inverso: Base de datos → Backend → Respuesta JSON → Frontend → Usuario.

6.3 Frontend

El frontend constituye la capa visible para el usuario. Sus principales responsabilidades serán:

  • Mostrar el catálogo y las categorías.
  • Permitir el filtrado y mostrar información detallada de los productos.
  • Administrar visualmente el carrito.
  • Presentar el panel administrativo.
  • Capturar información introducida por el usuario.
  • Validar aspectos básicos de formularios.
  • Realizar solicitudes HTTP hacia el backend.
  • Interpretar las respuestas recibidas y actualizar dinámicamente la interfaz.

El frontend no accederá directamente a la base de datos. Todas las operaciones relacionadas con información persistente deberán realizarse a través de la API REST. Se implementa como archivos estáticos (HTML, CSS, JS) servidos de forma independiente al backend.

6.4 Backend

El backend constituye el componente encargado de administrar la lógica del sistema. Está construido con Spring Boot 4.0.2 sobre Java 21. Sus principales responsabilidades serán:

  • Exponer endpoints REST bajo el prefijo /api/v1/.
  • Recibir y validar solicitudes mediante Jakarta Bean Validation.
  • Aplicar reglas de negocio (validación de stock, existencia de categorías, cálculo de totales).
  • Consultar y modificar información en MongoDB mediante Spring Data MongoDB (MongoRepository).
  • Controlar disponibilidad de productos.
  • Aplicar controles de seguridad (CORS configurado para orígenes permitidos).
  • Interactuar con la capa de persistencia.
  • Generar respuestas estructuradas en JSON.
  • Proporcionar documentación OpenAPI/Swagger.

El backend no será responsable de generar páginas HTML correspondientes al frontend.

6.5 Base de datos

El proyecto utiliza MongoDB 8 como motor de base de datos. MongoDB es una base de datos documental NoSQL que almacena la información en documentos JSON (BSON internamente). Se eligió por su flexibilidad para modelar datos de productos con atributos variables y por su integración nativa con Spring Data MongoDB.

Entorno principal: MongoDB Atlas (servicio gestionado en la nube de AWS, región US East 1), con un clúster de 3 nodos en réplica. La conexión se establece mediante una URI cifrada con TLS (mongodb+srv://), pasada como variable de entorno (MONGODB_URI) para no exponer credenciales en el código fuente.

Entorno de respaldo local: Un contenedor Docker con MongoDB 8, definido en docker-compose.yml, para desarrollo sin conexión a internet. Si no se proporciona la variable MONGODB_URI, la aplicación cae automáticamente al MongoDB local en localhost:27017.

6.6 API REST

La API REST funcionará como contrato de comunicación entre ambas aplicaciones. Las operaciones utilizarán métodos HTTP de acuerdo con su propósito: GET para consulta de información; POST para creación de nuevos recursos; PUT para actualización; y DELETE para eliminación.

Los endpoints están organizados bajo el prefijo /api/v1/:

RecursoRuta baseOperaciones
Categorías/api/v1/categoriasGET, POST, PUT, DELETE
Productos/api/v1/productosGET, POST, PUT, DELETE (filtro por categoría)
Carritos/api/v1/carritosPOST, GET, PUT, DELETE (gestión de ítems)

6.7 Formato JSON

Frontend y backend intercambiarán información principalmente mediante JSON (JavaScript Object Notation). La información de un producto podrá representar atributos como identificador, nombre, número del set, descripción, precio, stock, imagen y categoría. Este formato facilita la independencia tecnológica entre cliente y servidor.

6.8 Separación de responsabilidades

Capa de presentación: Representada por el frontend. Es responsable de interfaces, formularios, navegación, visualización de información e interacción con el usuario.

API y lógica de negocio: Representada por el backend. Es responsable de validaciones, reglas de negocio, servicios, seguridad y procesamiento de solicitudes. Organizada en capas: Controller (exposición REST) → Service (lógica de negocio) → Repository (acceso a datos).

Persistencia: Responsable del acceso y almacenamiento de datos relacionados con categorías, productos, carritos e ítems del carrito, mediante Spring Data MongoDB.

Base de datos: MongoDB, responsable del almacenamiento persistente y estructurado de la información en colecciones de documentos.

Este modelo permite reducir el acoplamiento entre componentes y facilita el mantenimiento, las pruebas y futuras ampliaciones.

7. Metodología de desarrollo

7.1 Metodología seleccionada: Kanban

Para el desarrollo del proyecto se utilizará Kanban, una metodología visual y liviana que permite organizar el trabajo sin la complejidad de ceremonias formales. Kanban se basa en un tablero donde cada tarea se representa como una tarjeta que avanza por columnas según su estado.

Kanban resulta adecuado para este proyecto porque:

  • No requiere roles especializados ni reuniones formales.
  • El flujo de trabajo es continuo: cada integrante toma la siguiente tarea disponible cuando termina la actual.
  • Es fácil de adoptar para un equipo universitario pequeño.
  • Se adapta al calendario semanal del curso, donde cada semana tiene un entregable definido.

7.2 Tablero Kanban

El tablero del proyecto tendrá tres columnas:

ColumnaSignificado
Por hacerTareas identificadas y pendientes de iniciar.
En progresoTareas en las que alguien está trabajando actualmente.
HechoTareas terminadas y verificadas.

Cada tarjeta del tablero corresponde a un requerimiento funcional, un requerimiento no funcional o una tarea técnica del cronograma semanal. El tablero se puede gestionar con GitHub Projects, Trello o cualquier herramienta equivalente.

7.3 Reglas del flujo

  • Cada tarea se vincula a un requerimiento o entregable semanal.
  • Una tarea no pasa a "Hecho" hasta que esté probada y funcional.
  • Al inicio de cada semana se revisan las tareas pendientes y se priorizan según el entregable de esa semana.
  • Al final de cada semana se verifica que las tareas comprometidas estén en "Hecho".

8.1 Semana 10 - Planeación

Durante esta semana se define completamente el proyecto antes de comenzar su implementación. Se elaboran el problema, objetivos, alcance, requerimientos, modelo de datos, arquitectura, metodología y cronograma. No se desarrolla todavía código correspondiente a la aplicación final.

8.2 Semana 11 - Backend inicial

Se inicia la implementación técnica del backend: estructura del proyecto con Spring Boot 4.0.2, conexión con MongoDB Atlas, primeros modelos (Categoria, Producto, Carrito, ItemCarrito), primeros servicios REST e incorporación inicial de Swagger/OpenAPI.

8.3 Semana 12 - CRUD y catálogo

Se implementará el CRUD completo de categorías y productos. Paralelamente se iniciará el frontend del catálogo consumiendo directamente los servicios REST desarrollados en el backend.

8.4 Semana 13 - Carrito y administración

Se implementarán el carrito de compras y el panel administrativo. El carrito permitirá agregar, eliminar y modificar cantidades, mientras que el panel permitirá gestionar productos y categorías desde la interfaz gráfica.

8.5 Semana 14 - Seguridad y calidad del frontend

La etapa estará enfocada en HTTPS, mitigación de XSS, protección CSRF, uso de SCSS y aplicación de un gestor de dependencias o automatizador.

8.6 Semana 15 - Integración y pruebas

Se realizará una verificación completa de CRUD, filtrado del catálogo, carrito, cálculo de totales, panel administrativo, comunicación frontend-backend, controles de seguridad, Swagger y comportamiento general de la aplicación.

8.7 Semana 16 - Despliegue y sustentación

La última etapa corresponde al despliegue de la aplicación en un entorno accesible. Deberá verificarse la disponibilidad de backend, frontend, base de datos, API, documentación Swagger y funcionalidades críticas desde un equipo externo al entorno de desarrollo.

9. Conclusiones de la etapa de planeación

La definición realizada establece una base técnica clara para la construcción de una tienda en línea modular especializada en productos LEGO. La solución busca resolver la dispersión del catálogo, la falta de control centralizado de productos y existencias y las limitaciones de un proceso de compra administrado manualmente mediante redes sociales.

La arquitectura desacoplada permitirá desarrollar el frontend y el backend de manera independiente, utilizando una API REST como único mecanismo de comunicación. Esta separación facilita el mantenimiento del sistema, mejora su capacidad de evolución y cumple con los lineamientos técnicos establecidos para el proyecto.

El modelo de datos propuesto, basado en MongoDB como base de datos documental, cubre las necesidades fundamentales relacionadas con categorías, productos y carrito de compras. El uso de documentos embebidos para los ítems del carrito sigue las mejores prácticas de diseño en bases de datos NoSQL, almacenando juntos los datos que se acceden juntos.

Los requerimientos funcionales y no funcionales permiten establecer criterios concretos para verificar posteriormente el cumplimiento del sistema.

Finalmente, la adopción de una metodología Scrum adaptada al contexto académico permite organizar las actividades entre las semanas 10 y 16 mediante hitos progresivos. De esta forma, el proyecto avanza desde la planeación y definición arquitectónica hasta la implementación del backend, frontend, seguridad, pruebas, documentación, despliegue y sustentación final.
